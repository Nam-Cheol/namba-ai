# Product Review

- Status: needs-revision
- Last Reviewed: 2026-05-20
- Reviewer: Namba Product Manager
- Command Skill: `$namba-plan-pm-review`
- Recommended Role: `namba-product-manager`

## Focus

- Challenge the problem framing, scope, user value, and acceptance bar before implementation starts.

## Findings

- `High` The problem statement is technically complete but still too runtime-centric for a pre-implementation product read. The SPEC explains many Codex 0.131 deltas, but it does not sharply state the primary user harm it is preventing: repos regenerated by Namba may become misleading, invalid, or double-guarded in active Codex sessions. That core failure mode should be named once in simpler terms so reviewers can evaluate tradeoffs against user value rather than against a changelog.
- `High` Scope is broad enough to invite implementation sprawl. The target surface list spans hook runtime, launchers, installers, Windows console behavior, project analysis, templates, generated docs, and multiple top-level docs, but the SPEC does not separate must-have compatibility work from opportunistic cleanup. Without that boundary, teams can keep expanding the work under the banner of "0.131 alignment."
- `Medium` Acceptance is strong on technical correctness but weak on product comprehension. Several criteria prove JSON validity and config determinism, but there is no explicit acceptance item that a maintainer can tell which boundary belongs to Codex interactive safety versus `namba run` evidence validation after reading the updated docs. That understanding is a core part of the stated goal.
- `Medium` The Codex 0.131 compatibility boundary is mostly understandable, but it is spread across Scope, Compatibility Requirements, and Documentation Requirements instead of being reduced to one stable definition. A short canonical statement would reduce ambiguity: what Namba owns, what Codex owns, and what Namba must not persist in repo-managed config.
- `Medium` User value is implied for maintainers and contributors, but the intended audience is not named explicitly. This matters because the documentation asks are large. The SPEC should say whether success is aimed at Namba maintainers, repo owners regenerating assets, contributors debugging hook behavior, or all three. That will help constrain doc depth and examples.

## Decisions

- Product review does not support implementation as-is without tightening scope language and acceptance framing.
- The SPEC should remain focused on compatibility hardening, not on redesigning Namba's broader Codex integration model.
- Documentation is in scope because boundary misunderstanding is part of the problem, but docs should prove operator understanding rather than expand into a general Codex tutorial.

## Follow-ups

- Add a one-paragraph "Primary outcome" or "User impact" statement to `spec.md` that describes the concrete failure modes being prevented in plain language.
- Split scope into `required for 0.131 compatibility` versus `deferred follow-up` so Windows, installer, and project-analysis changes are only included when directly necessary for the compatibility boundary.
- Add at least one acceptance item that verifies docs make the ownership boundary understandable:
  `a maintainer can distinguish .codex/hooks.json interactive guardrails from .namba/hooks.toml validation/evidence policy, and can identify which Codex runtime settings must remain user/session owned`.
- Add a brief audience line in the SPEC or docs requirements naming the primary readers for the compatibility guidance.
- Consider marking `install.ps1`, `project_analysis.go`, and `console_windows.go` as conditional touch points rather than assumed implementation targets unless the audit proves they are required.

## Recommendation

- `Revise before implementation.`
- The SPEC is directionally correct and product-justified, but it needs a tighter statement of user harm, clearer must-have scope boundaries, and one acceptance criterion for human understanding of the Codex 0.131 compatibility boundary before engineering starts.
