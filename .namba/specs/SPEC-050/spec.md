# SPEC-050

## Title

Codex 0.131 core compatibility for NambaAI safety surfaces

## Problem

Codex 0.131 changes several core surfaces that NambaAI depends on for safe
interactive use: plugin-bundled hooks are default-enabled, the hook trust flow
is more visible, PreToolUse can rewrite input through `updatedInput`,
session-aware hook behavior is expanding, legacy hook and config paths are being
removed, strict config parsing is more important, the TUI exposes service tier,
approval mode, permissions, and effective workspace roots, Windows sandbox
behavior is stricter, and Git helper commands now ignore configured repository
hooks in some paths.

NambaAI must align generated Codex-facing assets with that runtime without
weakening its own safety model or confusing the boundary between Codex
interactive guardrails and Namba run evidence validation.

## Goal

Update NambaAI's Codex-facing safety, config, hook, installer, and
documentation surfaces so a repo initialized or regenerated by NambaAI remains
deterministic, valid, and understandable under Codex 0.131.

## Primary Outcome

After this work, maintainers, repo owners, and contributors should not be
misled by stale generated assets. A regenerated NambaAI repo must not install
invalid Codex config, run the Namba guard twice because plugin hooks are also
enabled, imply that Namba owns session-specific Codex permission choices, or
hide the difference between interactive Codex protection and `namba run`
validation evidence.

## Scope

### Required For Codex 0.131 Compatibility

- Audit the current Codex hook config, generated config TOML, Namba hook runtime,
  guard scripts, tests, templates, project analysis, Windows helpers,
  PowerShell installer, and generated docs against Codex 0.131 behavior.
- Update hook config and runtime handling for `SessionStart`,
  `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, and
  `Stop`.
- Ensure PreToolUse handling supports safe `updatedInput` rewrites without
  weakening command blocking, path boundaries, or prompt-refinement behavior.
- Apply `PreToolUse` decisions in this order: malformed payloads still produce
  valid JSON, deny/block decisions beat rewrites, and rewrites only apply to
  inputs that are already allowed.
- Ensure session-id hook behavior is accepted, preserved where useful, and does
  not make guard output invalid when the field is absent or renamed upstream.
- Ensure plugin-bundled hooks cannot trigger duplicate Namba guard execution.
- Place duplicate-hook prevention at the interactive Codex boundary: generated
  `.codex/hooks.json`, launcher scripts, and shared guard behavior. Do not rely
  on `.namba/hooks.toml` or the Namba runner runtime to dedupe interactive Codex
  hook execution.
- Remove or stop generating legacy hook and config surfaces that Codex 0.131 no
  longer expects.
- Keep generated `.codex/config.toml` deterministic and valid under strict
  parsing.
- Keep repo-managed config limited to repository-safe defaults. Do not encode
  user-specific model, auth, installed apps, web-search, sandbox, or approval
  choices.
- Resolve the existing `namba codex access` contract explicitly: either preserve
  its current repo-safe baseline behavior with matching tests and docs, or
  deliberately narrow/remove repo-managed `approval_policy` and `sandbox_mode`
  ownership in the same implementation slice. Do not leave generated config,
  CLI behavior, and docs disagreeing.
- Document how Codex now displays service tier, status-line data, permissions,
  approval mode, and effective workspace roots without taking ownership of those
  user/session choices.
- Document that Git helper behavior may ignore configured repository hooks, so
  Namba safety cannot rely on Git hooks alone.

### Conditional Touch Points

- Update `install.ps1`, `internal/namba/project_analysis.go`, and
  `internal/namba/console_windows.go` only where the audit proves they are
  required for the Codex 0.131 compatibility boundary.
- Align docs and tests with Windows deny-read parity, scoped write roots,
  ineffective firewall policy handling, PowerShell profile avoidance,
  unsupported PowerShell stop-parsing forms, and quoted path behavior only where
  those surfaces affect generated Codex assets or documented Namba guidance.

## Out Of Scope

- Changing the user's selected model, authentication method, installed plugins,
  app connectors, web-search preference, sandbox mode, approval mode, or service
  tier.
- Weakening dangerous command blocking, approval risk notes, prompt refinement,
  final report guardrails, or repo-safe config boundaries.
- Collapsing `.codex/hooks.json` and `.namba/hooks.toml` into one authority.
- Replacing Namba's validation boundary with Codex interactive hook behavior.
- Adding a broad new hook framework unrelated to Codex 0.131 compatibility.
- Redesigning the Namba command surface.

## Compatibility Requirements

1. `.codex/hooks.json` remains the Codex interactive guardrail.
2. `.namba/hooks.toml` remains the Namba run evidence and validation boundary.
3. Generated Codex config is deterministic across repeated regeneration.
4. Generated Codex config parses under Codex 0.131 strict config expectations.
5. Repo-managed config avoids user-specific runtime choices.
6. Default-enabled plugin hooks do not cause duplicate Namba guard execution.
7. Hook outputs are always valid JSON, including deny, allow, rewrite,
   continue, and failure paths.
8. Hook failures fail safely with structured JSON and useful diagnostics.
9. Permission and approval display changes are documented as Codex UI/runtime
   state, not as Namba-owned policy.
10. Effective workspace roots and scoped write roots are documented clearly for
    maintainers and users.

## Hook Event Requirements

- `SessionStart`: accept Codex 0.131 session metadata, including session-id
  fields when present, and emit valid JSON on startup, resume, and missing-field
  cases.
- `UserPromptSubmit`: preserve prompt-refinement behavior and approval risk
  notes; never emit malformed JSON for empty, quoted, or multiline prompts.
- `PreToolUse`: preserve dangerous command blocking and support safe
  `updatedInput` rewrites where Codex accepts them.
- `PermissionRequest`: preserve approval-risk guidance and emit valid JSON for
  shell and file permission prompts.
- `PostToolUse`: emit valid JSON for successful, failed, and missing-output tool
  payloads.
- `Stop`: preserve final report guardrails and emit valid JSON for normal stop,
  interrupted stop, and missing-field payloads.

## Launcher Requirements

- POSIX launcher handles missing Python, quoted repository paths, stdin JSON,
  and Python guard failure JSON correctly.
- Windows PowerShell launcher handles missing Python, quoted repository paths,
  stdin JSON, and Python guard failure JSON correctly.
- PowerShell launch avoids profile loading.
- PowerShell launch avoids unsupported stop-parsing forms in contexts where
  Codex or Windows wrappers do not support them.
- Failure output is structured JSON rather than shell tracebacks or raw stderr
  whenever practical.

## Test Strategy

- Extend Go tests around hook runtime, guard behavior, template generation,
  project analysis, Windows console helpers, and deterministic config output.
- Add or update fixtures that simulate Codex 0.131 hook payloads for all six
  hook events.
- Exercise duplicate plugin hook prevention.
- Exercise POSIX and PowerShell launcher behavior through deterministic local
  tests without requiring live Codex execution.
- Keep validation command coverage aligned with project docs:
  `go test ./...`, `go vet ./...`, and `gofmt -l "cmd" "internal"
  "namba_test.go"`.

## Documentation Requirements

- `README.md`, `README.ko.md`, and `AGENTS.md` explain the Codex 0.131
  compatibility boundary in practical terms.
- Documentation follows this order where the boundary is discussed:
  what Codex displays, what repo-managed Namba assets generate, what Namba
  validates, and what Namba cannot rely on or control.
- Documentation includes a compact terminology table or equivalent contrast for
  `approval mode`, `permissions`, `effective workspace roots`,
  `scoped write roots`, `.codex/hooks.json`, and `.namba/hooks.toml`.
- Documentation avoids language that says or implies Namba sets Codex
  permissions, owns workspace roots, or persists user/session choices such as
  approval mode or service tier through repo-managed config.
- Generated Codex and Namba docs explain workspace roots, permission display,
  scoped write roots, Windows deny-read parity, ineffective firewall policy
  handling, PowerShell profile avoidance, and Git helper hook limitations.
- Docs state that `.codex/hooks.json` protects interactive Codex sessions while
  `.namba/hooks.toml` remains the Namba run evidence/validation boundary.

## Risks

- Codex 0.131 hook semantics may evolve further; mitigate with tolerant input
  parsing and strict output validation.
- Duplicate guard execution may be easy to miss if plugin hooks and repo hooks
  both install the same command; mitigate with generated config tests and
  runtime guard dedupe tests.
- Strict config parsing can fail on harmless-looking user-specific defaults;
  mitigate by keeping repo-managed config narrow and deterministic.
- Windows sandbox and PowerShell behavior is easy to under-test on non-Windows
  hosts; mitigate with parser/unit coverage and clearly skipped integration
  coverage where a native shell is unavailable.
- Git helper commands ignoring repo hooks may create a false sense of safety;
  mitigate by documenting the limit and keeping Namba validation independent.
